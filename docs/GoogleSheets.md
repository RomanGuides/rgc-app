# Google Sheets Content Pipeline

This document describes where this app's content data comes from — and, just as importantly, what this repository does and does not contain.

## What this repo contains

This repository (`rgc-app`) contains only the **output** of the content pipeline: static JSON files checked into `src/data/` (places, guides, experiences, testimonials, app content). There is no code in this repo that talks to Google Sheets, no export script, and no scheduled/automated sync.

The evidence for this is a comment in `src/services/placesService.ts` stating the places JSON is `generato da export_places.py a partire dal Google Sheet` ("generated by `export_places.py` from the Google Sheet") — that script lives outside this repository, in the separate `RomanGuides` project/pipeline, not here.

## Implication for updating content

Updating place/guide/experience/testimonial data today is a **manual, out-of-band process**:
1. The source of truth (a Google Sheet) is edited directly.
2. An external export step (the `export_places.py` script mentioned above, or an equivalent manual export for the other entities) regenerates the JSON.
3. The regenerated JSON is copied into this repo's `src/data/` and committed.

There is no CI job, webhook, or build step in this repository that fetches fresh data automatically — every deploy of this app ships whatever JSON was last committed, until someone repeats the manual export-and-commit step above.

## Why this split exists

Keeping the export pipeline in a separate project keeps this app a pure static frontend with zero external runtime dependencies (no API keys or network calls needed just to load place data), at the cost of content updates requiring a manual step rather than being live/automatic. This is a real limitation worth tracking — see the "content update workflow" item in `ROADMAP.md`.
