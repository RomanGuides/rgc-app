# Changelog

All notable changes to this project are documented in this file, starting from the v1.0.0 baseline. Format loosely follows [Keep a Changelog](https://keepachangelog.com/).

## [Unreleased]

### Added
- Capacitor native wrapper for iOS and Android (`ios/`, `android/`, `capacitor.config.ts`), enabling native App Store/Play Store builds of the existing web app. No app logic changed — geolocation still uses the standard browser API, not a native plugin (deferred to a future change). Location permission strings declared on both platforms (`NSLocationWhenInUseUsageDescription` on iOS, `ACCESS_COARSE_LOCATION`/`ACCESS_FINE_LOCATION` on Android).
- `npm run cap:sync` / `cap:ios` / `cap:android` scripts for the native build workflow.
- `.gitignore` hardened for native signing material (`*.jks`, `*.keystore`, `*.mobileprovision`).
- `@capacitor/dialog` dependency, used in place of `window.alert()` (see Fixed below).
- Redesign v1 — "Empty and Error States" addendum: search-no-match suggestion pills (`SearchScreen.tsx`, computed entirely from the bundle via Levenshtein name-matching, `src/utils/levenshtein.ts`), zero-category-results messaging with two distinct recovery actions (`RomeSheet.tsx`), a by-neighbourhood grouped view replacing "Nearest to you" when location is explicitly denied (new `'denied'` status in `useGeolocation.ts`, distinct from a timeout/unsupported `'fallback'`), an offline banner + permanent map background color so failed tiles never show a grey checkerboard (`useOnlineStatus.ts`, `OfflineBanner.tsx`), and a broken-image fallback on `PlaceScreen.tsx`'s header. `EmptyState.tsx` reworked to the addendum's visual rules (left-aligned, 40px outline icon, text actions instead of buttons).
- In-app Bokun booking widget (`BookingWidgetModal.tsx`): "Discover Experience" on the Experiences tab now opens Bokun's hosted checkout inside a full-screen in-app view instead of handing off to the system browser. Uses Bokun's own official embed mechanism (their `BokunWidgetsLoader.js` script, loaded once per app session, plus a `<div class="bokunWidget" data-src="...">` placeholder that their script detects and takes over) — no Capacitor plugin needed, since the whole app already runs inside one WebView. Bokun remains fully responsible for the booking and payment flow — no backend, no API keys, no PCI scope taken on for this. See `docs/BokunIntegration.md` for the full comparison against a native REST v1 checkout and why the embedded widget was chosen for now.
- `scripts/check-place-areas.mjs`, run at the start of every `npm run build`: fails with a clear message if any place's `area` is missing or outside the 27 hand-confirmed canonical neighbourhood names, so a future Google Sheet re-export can't silently wipe that manual work (see `docs/DataModel.md`). All 89 places' `area` values were normalized to this canonical list as part of this change (16 places corrected — the rest were already consistent from an earlier pass); no other field changed.
- Experiences tab restructured around five sections (masthead, the seven tours, Meet the Guides, What guests say, Our Story) — it now also carries the "who we are" content that used to live on the Saved tab (My Rome). Saved tab (`MyRomeScreen.tsx`) reduced to the shortlist only: title, count, and the saved-places list, now sorted by distance. Structure/layout only for the Experiences move — final copy (masthead phrase, guide bios, quotes) still pending; content that didn't fit either screen's new structure (discount banner, alternate night-angle tour copy, per-guide WhatsApp button, TripAdvisor review link, "videos coming soon" card) was moved to `docs/parked-content.md` rather than deleted.
- Category filter icons (`CATEGORY_ICONS` in `Icons.tsx`): six new outline icons (utensils, pizza, gelato, rooftop bar, cocktail bar, gallery) replace the emoji in `RomeSheet.tsx`'s filter popover — the last spot in the app still using emoji. Two design docs (`Icons Addendum`, `Handoff Diff`) explicitly say categories should keep their emoji and that no icon registry is wanted — confirmed with the team that guidance is superseded before building this. Not defined anywhere, so designed from scratch, matching the established 24×24/stroke-2/round-caps/no-fill convention.
- Category placeholder photos for `PlaceScreen.tsx`'s header: gastronomic categories (restaurant, pasta, pizza, gelato, rooftop_bar, cocktail_bar) fall back to a bundled photo when a place has no `imageUrl` of its own, tried after the place's real photo and before the flat `#F3EFEB` fallback. `gallery` (the one non-gastronomic category) keeps the flat fallback; a generic monument photo would be misleading. **Path correction, 2026-08-06:** this originally shipped as a runtime string path (`/assets/category/<category>.jpg`, implying `public/assets/category/`) since real photos didn't exist yet. Once real photos arrived, the content brief specified everything under `src/`, so this was rewritten to static Vite imports from `src/assets/category/<category>.jpg` instead — Vite guarantees the file exists at build time rather than 404ing silently at runtime. `public/assets/category/` was never correct and nothing was ever shipped there; the six files live at `src/assets/category/`, named exactly to the `PlaceCategory` keys (underscores, not hyphens: `rooftop_bar.jpg`, `cocktail_bar.jpg`).
- `@capacitor/app` dependency, used only so `BookingWidgetModal.tsx` can intercept the Android hardware back button (see Fixed below); no other use yet.
- `BookingWidgetModal.tsx` brought up to the full checkout-embed spec: a close (✕) control instead of a back chevron — closing a checkout is a dismissal, not a backward navigation step; a trust row under the tour name (padlock + hostname, 12px `#6E645F`) so the person about to enter a card has some visible signal the page is the real widget; a 3px indeterminate loading bar plus skeleton blocks on first load (never a blank white screen); and a dedicated error state — triggered by an explicit `onError` or a ~10s load timeout (iframes don't reliably fire `onError` for most real failures, so the timeout is the actual detection mechanism) — offering three actions: Try again, Open in browser, and a placeholder "Contact us" (`LINKS.SUPPORT_CONTACT_URL`, a `mailto:` placeholder pending the founder's real support address). Three actions on one screen is deliberately more than anywhere else in the app — a dead end here is a lost booking.
- **Verified limit, not an assumption:** reading a cross-origin iframe's current URL from the parent page is blocked outright by the browser's same-origin policy — a hard platform boundary, not a bug to fix. Since we supply the widget's `data-src` ourselves, the trust row's initial hostname is known synchronously and doesn't depend on this at all; the component also reads Bokun's own internal iframe's `src` attribute directly once it appears (an element in our own DOM, not a cross-origin document read) as a best-effort improvement if it navigates further. For the native "new window" relay case (see Fixed below), the URL likewise comes from our own code, not from peeking into an iframe. Only a navigation the widget makes entirely on its own, with neither of those signals available, falls back to a neutral "Secure payment page" rather than fabricating a hostname.
- **Legal & About screen** (`src/features/legal/LegalScreen.tsx`) — privacy policy, terms of service, app version, and contact, reachable from a plain text link in `RomeSheet`'s full-detent footer (next to Get Around/Emergency/Find Water Nearby), not a tab or a Settings screen — required before either app store listing can go live, since both require an in-app-reachable privacy policy and the app uses location. Copy lives in `src/config/legal.ts`, same pattern as `story.ts` (hand-written, not sourced from the Google Sheets content pipeline — legal text shouldn't be editable from a spreadsheet without review). **This copy is a draft reflecting actual app behavior (no accounts, on-device-only saves, OpenRouteService for directions, Bokun for booking/payment, no analytics/tracking), not a legally reviewed final text — tracked in `ROADMAP.md` as a publication blocker until reviewed.**
- Real support contact address confirmed by the founder: `LINKS.SUPPORT_CONTACT_URL` is now `mailto:info@romanguides.com`, replacing the `support@romanguides.com` placeholder used by `BookingWidgetModal`'s error state and now also `LegalScreen`'s contact line.
- **WelcomeScreen** (`src/features/welcome/WelcomeScreen.tsx`), shown once per install, before any tab. Previously the app requested location only on an explicit compass tap — no cold dialog at launch, but still a context-free ask the first time it happened, and on iOS the system dialog only shows once ever, so a reflexive "no" there is permanent. Full-screen hero photo (`appContent.json`'s existing "hero" entry), dark gradient over the bottom third for legibility even if the photo fails to load, "Rome, from people who live here." (reusing `OUR_STORY_MASTHEAD`), one line of body copy, a primary button ("Show me what's nearby") that triggers the location permission prompt either way and proceeds regardless of the answer, and a "Not now" text link that proceeds without asking at all. No carousel — deliberately one screen. Shown-once state lives in `usePlacesStore`'s existing persisted slice (`hasSeenWelcome`), not a separate localStorage key.
- `MapScreen.tsx` now checks `navigator.permissions.query({name:'geolocation'})` on mount and auto-requests location immediately if the permission is already decided (granted or denied — from Welcome, or a previous session), so "Nearest to you" (or the by-neighbourhood list, if denied) is populated right away instead of needing a compass tap first. Deliberately does **not** auto-request while permission is still `'prompt'` (undecided) — doing so would silently trigger the OS dialog after a "Not now", defeating the entire point of deferring it. Falls back to no auto-request if the Permissions API is unavailable, same as before this change.
- **`RomeSheet`: a resolved-but-distant location no longer shows "Nearest to you" with nonsensical distances.** If location access is granted but resolves far from Rome — at home before the trip, at the airport, anywhere more than 50km from the city center — the previous behavior sorted the 89 places by real distance anyway, surfacing entries like "9,000 km away". Reuses the same by-neighbourhood grouped list already built for the explicit-denial case (`RomeSheet.tsx`'s `areaGroups`), since the practical need is identical: real distance sorting isn't useful yet either way. 50km comfortably covers Rome's whole metro area (Fiumicino ~30km, Ciampino ~15km from center) without triggering for someone already in town.
- **Location "priming" outside first launch.** If the user tapped "Not now" on `WelcomeScreen` and later taps the compass (`LocateButton`) for the first time, the OS permission is still undecided (`'prompt'`) — previously that tap went straight to the system dialog with no context, and on iOS that dialog only shows once ever, so a reflexive "no" there is permanent. `MapScreen.tsx`'s `handleLocateMe` now checks `navigator.permissions.query` on tap: while still `'prompt'`, the first tap only shows a one-line explanation ("Turn on location to sort by how far away things are.") near the button instead of requesting anything; a second tap then actually asks. Once permission is decided (either way), behavior is unchanged — immediate request, same as before. Session-only, not persisted: a restart re-explains if still undecided, which is fine, since there's no dialog burned yet either way. **The hint renders below the button, not above as originally specified** — not enough vertical room above it for two lines of text without the hint itself overlapping and intercepting taps on the button (found via a failing Playwright test). Built and tested via Playwright without a physical device available overnight — flagged in `ROADMAP.md` for a real-screen look, consistent with this project's history of floating-over-the-map layout surprises.

### Fixed
- **Map screen, two real-device layout overlaps.** (1) MapLibre's `NavigationControl` (the zoom +/- buttons, top-right of the map) is anchored by the library at `top: 0` with no notion of the notch/status bar, so it rendered underneath the clock/battery icons — every other floating element above the map (`LocateButton`, `OfflineBanner`) already accounts for `env(safe-area-inset-top)`, this was the one left out. Fixed with a global CSS rule on `.maplibregl-ctrl-top-right` (`tokens.css`). (2) `RomeSheet`'s header (search bar + category filter button) sits at the sheet's top edge, which rises into the same top-right corner as `LocateButton` (🧭/📍) once the sheet reaches its `full` detent (90% of the screen) — `LocateButton`'s z-index is deliberately higher than the sheet's (needed for the filter popover, see below), so the filter button visually disappeared underneath the compass instead of the other way round. Fixed by fading `LocateButton` out (opacity + `pointer-events: none`) whenever the sheet reaches `full`, the same way Google Maps-style sheets hide floating controls once they dominate the screen — `RomeSheet` now reports its detent back to `MapScreen` via a new `onDetentChange` callback prop.
- **Bokun's own "Go to cart" button did nothing on tap**, reached right after choosing a tour's date/time — confirmed on a real device, not caught by any test or emulator. Real root cause, found through a live on-device debugging session with Chrome DevTools remote-inspecting the physical phone (`chrome://inspect`): the original implementation rendered Bokun's widget as a plain `<iframe src={bookingUrl}>`, but that's not Bokun's actual embed mechanism — their official embed (visible in the Bokun admin's widget-embed-code generator) is a `<script src=".../BokunWidgetsLoader.js?bookingChannelUUID=...">` plus a `<div class="bokunWidget" data-src="...">` placeholder that their own script detects (via a `MutationObserver`) and takes over, creating its own internal iframe and handling cart/checkout itself. A bare iframe never gave their code anything to hook into for that step: on-device testing proved the tap landed on exactly the right button (`document.elementFromPoint` at its true coordinates, ruling out an invisible overlay) and that even a direct `.click()` via the JS console produced zero effect — no DOM change, no network request, no console error, no `postMessage` — same as the real tap, ruling out a WebView touch/click-translation issue. Two earlier hypotheses (Capacitor's default `onCreateWindow` silently dropping `window.open()`; `shouldOverrideUrlLoading` treating nested-iframe navigation as an external Intent) were tried first and diagnostically disproven via native logging before the real cause was found — both fixes (`RomanGuidesWebChromeClient`, `RomanGuidesWebViewClient`) are kept anyway as general hardening for a real, separate risk: a payment popup (3-D Secure/PayPal/Apple Pay) opening from inside Bokun's own widget iframe. Fixed by switching `BookingWidgetModal.tsx` to Bokun's real embed mechanism — verified end-to-end on the same physical device: "Go to cart" now opens the real cart, and the flow proceeds through participant/contact details to the card-entry step. iOS has the same `onCreateWindow`-equivalent gap (`WKWebView`'s `WKUIDelegate.createWebViewWith`) for the payment-popup case only — not written in this pass, since this project has had no Mac/Xcode available to build or verify it (see `ROADMAP.md`).
- `PlaceScreen.tsx`'s header fell back to `meta.color` (the category's map-marker color) when a place had no image, or a broken one. For `restaurant`/`pasta` that color is `#ff0033` — close enough to brand red that a full-screen header in it reads as an error state. Changed the fallback to `#F3EFEB` (or a category placeholder photo first, see Added) — `meta.color` is no longer used for this at all.
- `RomeSheet.tsx`'s category filter popover rendered inside the sheet's own `overflow: hidden` box, which also establishes its own stacking context at a lower z-index than `LocateButton`'s. Its local `zIndex: 6` could never out-rank `LocateButton` (z-index comparisons don't cross stacking-context boundaries) and got clipped/covered by it whenever the sheet was tall enough for the two to overlap. Rewritten to render through a `createPortal` into `document.body`, positioned from the filter button's real `getBoundingClientRect()` (flips to open upward if there isn't enough room below), with a full-screen transparent backdrop that closes it on tap.
- `BookingWidgetModal.tsx` had no Android hardware-back handling, so pressing it would fall through to Capacitor's default behavior — navigating the embedded iframe's own history (unexpected, and could silently step backward through a checkout flow) rather than closing our modal. `@capacitor/app`'s `backButton` listener, registered only while the modal is mounted, now closes it directly; no effect on iOS/web, where that event never fires.
- Found only by testing a real installed Android build (not caught by Playwright or browser testing): the bottom tab bar and the Map screen's top black bar had no safe-area padding, so on a device with a 3-button navigation bar and a standard status bar, both were rendered underneath system UI — the tab bar became untappable, and the top bar sat behind the clock/signal icons. Fixed with `env(safe-area-inset-bottom)` / `env(safe-area-inset-top)` padding in `src/App.tsx` and `src/features/map/MapScreen.tsx`.
- Also found only on a real device: `startWalkingDirections.ts` used `window.alert()` for its two user-facing error messages (no location set, route request failed). In Capacitor's native Android WebView this caused the app to freeze, requiring a force-close — a known incompatibility between raw browser dialogs and native WebViews. Replaced with `@capacitor/dialog`'s `Dialog.alert()`, which has an identical web fallback (no change in browser/Playwright behavior) but uses a proper native dialog on Android/iOS.
- The route-line effect in `MapView.tsx` depended on the whole `activeRoute` object, which gets a new reference on every location update while a route is active (`updateRouteProgress`) — this re-ran `map.fitBounds()` on every GPS tick, which was harmless indoors but saturated the render thread outdoors with frequent real GPS updates, causing an ANR requiring a force-close. Narrowed the dependency to `activeRoute?.destinationId`.
- `useGeolocation.ts`'s continuous `watchPosition` (used during an active route) briefly went through `enableHighAccuracy: false` as an attempted mitigation for the ANR above, on the theory that our own high-accuracy request was contributing to device-wide CPU/GPS contention. On a real device this produced a ~200m position error (WiFi/cell-based positioning instead of real GPS) — enough to break arrival detection (25m threshold). Reverted to `enableHighAccuracy: true`: the ANR's actual CPU breakdown showed other background apps and `system_server` as the dominant load, not this app's own accuracy setting, so the precision cost wasn't justified by the marginal ANR benefit.
- Starting a walking route froze the app immediately on a real device (confirmed via `adb logcat`: a brand-new GPS watch registered with the OS every ~15-20ms, non-stop). Root cause was the same class of bug as the `MapView.tsx` fix above, in a different effect: `MapScreen.tsx`'s tracking effect (`startWatching`/`stopWatching`) depended on the whole `activeRoute` object, which gets a new reference on every position update — each new reference re-ran the effect's cleanup and body, registering a fresh `watchPosition` in a tight loop, made worse by the `enableHighAccuracy: true` revert above producing far more frequent real position updates than before. Narrowed the dependency to `activeRoute?.destinationId`, same fix as `MapView.tsx`.

### Removed
- `src/features/home/` (`HomeScreen.tsx`, `homeConfig.ts`) — the pre-redesign Home tab, unrouted since the 5→3 tab cut (`App.tsx` only ever mounted `map`/`experiences`/`myrome`) but never deleted. Confirmed zero references anywhere else in the codebase before removal; bundle output (`dist/assets/index-*.js` size) was unchanged, confirming it was never actually reachable from the shipped app.

## [1.0.0] — 2026-08-01

### Added
- First Playwright end-to-end test suite for this app: Home, Map (basemap + markers), Explore, My Rome, marker popup, Directions (full flow: locate → select place → get directions → route drawn → stop route), and a layout-regression test for the email capture form's "Last name" field.
- Optional HTTPS-enabled local preview (`HTTPS=true npm run preview -- --host`), via `@vitejs/plugin-basic-ssl`, needed to test real GPS geolocation from a phone on the local network (mobile browsers require a secure context for the Geolocation API).
- `.gitignore` entries for Playwright artifacts (`playwright-report`, `test-results`, `blob-report`) and for common credential/certificate file patterns.

### Fixed
- Map: a fallback timer could call `map.addSource()` before the style finished loading, throwing "Style is not done loading." This silently broke both marker clustering and the Walking Directions route line, since both are set up in the same function. Fixed by checking `map.isStyleLoaded()` before proceeding, deferring to the real `load` event otherwise.
- Email capture form: the "Last name" input was clipped on narrow phone screens, a standard flexbox `min-width: auto` issue on two `flex: 1` inputs in a row. Fixed with explicit `minWidth: 0`.
- Geolocation: the one-shot `requestLocation()` call used a 6-second timeout, too short for a real first GPS/network fix on a physical device (especially indoors) — it reliably timed out and silently fell back to the hardcoded Trevi Fountain reference point. Raised to 15 seconds; confirmed fixed on a real phone.

### Removed
- Dead code, verified unreferenced anywhere in the codebase before removal: `src/services/collectionsService.ts`, `src/data/collections.json`, `src/utils/directions.ts`, `src/assets/` (unused template assets: `hero.png`, `react.svg`, `vite.svg`), `public/icons.svg`.
- Unused `catch` binding in `scripts/check-bundle-size.mjs`.

### Documentation
- Added `RELEASE_NOTES.md`, `docs/` (Architecture, Data Model, Map, Routing, Google Sheets, Deployment), `CONTRIBUTING.md`, and `ROADMAP.md`.
