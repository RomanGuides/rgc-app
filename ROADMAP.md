# Roadmap

Future work under consideration, grouped by priority. Nothing in this document is implemented — it exists to track deferred decisions and known gaps so they aren't lost or rediscovered from scratch. Per `CONTRIBUTING.md`, anything here should be discussed before implementation begins.

## High priority

- **CI/CD pipeline.** No `.github/workflows` or equivalent exists. At minimum: run `npm run build` and `npm run test:e2e` automatically on every push/PR, so a broken build or failing test can't reach `main` unnoticed.
- **Hosting/deployment configuration.** No hosting target (Netlify, Vercel, static bucket, etc.) is configured. `dist/` is currently published manually, if at all.
- **Move the OpenRouteService API key server-side before any public store launch.** The key lives client-side today (`src/config/routing.config.ts`), fine for local/private testing, but once the app is distributed via the App Store/Play Store it ships inside the public binary, extractable by anyone — a real cost/abuse risk at public scale. Needs a small proxy/backend before a real public launch.
- **App Store / Play Store submission.** The native wrapper exists (`ios/`, `android/`, via Capacitor — see `docs/Deployment.md`), but no developer accounts, signing, or store listings have been set up yet. Real next step whenever store distribution is prioritized; needs its own discussion given the account/compliance work involved (privacy policy, Data Safety form, screenshots, etc.). **Screenshots specifically need fresh real-device captures, not reuse of any earlier reference mockups** — the redesign (2026-08-05, see `RELEASE_NOTES.md`) changed the nav shell, every major screen, and added in-app booking, so anything captured before that point no longer reflects the app.
- **iOS equivalent of `RomanGuidesWebChromeClient` (Android).** Capacitor's default WebView doesn't implement window-open handling, so any `target="_blank"`/`window.open()` from content inside Bokun's widget silently does nothing. This turned out **not** to be what was blocking "Go to cart" (that was a different, now-fixed bug — see `docs/BokunIntegration.md` and `CHANGELOG.md`), but it's still a real, separate risk for a payment popup (3-D Secure/PayPal/Apple Pay) opened from inside Bokun's widget. Fixed for Android with a custom `WebChromeClient` (`android/app/src/main/java/com/romanguides/app/RomanGuidesWebChromeClient.java`) that relays the target URL back into the app instead of dropping it. `WKWebView` (iOS) has the same category of gap (`WKUIDelegate.createWebViewWith`, also unimplemented by Capacitor's default iOS bridge) and almost certainly needs the equivalent fix — not written yet because this whole project has had no Mac/Xcode available to build or test it; shipping unverified native Swift felt worse than leaving a documented gap. See `docs/BokunIntegration.md`.
- **Real-card booking test through to a successful charge, iOS.** Verified on Android (2026-08-05): a full booking with a real European card went through end-to-end, including 3-D Secure, with no framing issues. Same test still needs doing on iOS once the `WKWebView` equivalent of the item above exists — there's no reason to expect a different result, but it hasn't been run on that platform. See `docs/BokunIntegration.md`.
- **Legal review of the Privacy Policy / Terms of Service text.** `src/config/legal.ts` (feeding `LegalScreen.tsx`) is a draft written to accurately describe actual app behavior (no accounts, on-device-only saves, OpenRouteService for directions, Bokun for booking/payment, no analytics/tracking) — not legally reviewed. Must be reviewed (ideally by the founder and a lawyer familiar with GDPR, since the app serves EU tourists) before any App/Play Store submission.

## Medium priority

- **Real-device visual check for the location-priming hint (`MapScreen.tsx`, 2026-08-06).** Built and verified via Playwright overnight, without the user available for a physical-device look — this project's own history (zoom control under the status bar, filter button under the compass, both found only on a real phone) is reason enough to flag any new floating-over-the-map text as needing one. Specifically: the hint renders *below* `LocateButton` rather than above it as originally specified — there isn't enough vertical room above the button (`top: safe-area-inset-top + 62px`) for two lines of text without the hint overlapping and intercepting taps on the button itself, discovered via a failing Playwright test, not a hunch. Worth eyeballing on a real screen to confirm it reads well and doesn't collide with anything else near that corner.

- **Native Bokun booking integration (REST v1 + backend).** Full architecture in `docs/BokunIntegration.md` §1–§9 — experience listing, availability/pricing, native checkout, and booking retrieval, all through Bokun's REST API behind a new backend (Bokun's auth model signs every request, including reads, with the secret key — so a backend proxy is required for any of it, not just checkout). **Deliberately deferred**, not merely unscheduled: as of 2026-08-05 the booking-widget-in-app-frame approach (see `CHANGELOG.md`) already gets Roman Guides out of the external-browser handoff at zero backend/PCI cost, and the remaining gap — UI/branding control over the checkout screen itself — wasn't judged worth taking on permanent backend and payment operational responsibility for at current volume. Revisit if that calculus changes (e.g. a business decision to move to Roman Guides' own independent Stripe settlement, `docs/BokunIntegration.md` §2.1 Option B).
- **Content update workflow.** Updating place/guide/experience data currently requires manually re-running an external export script and hand-copying JSON into this repo (see `docs/GoogleSheets.md`). Worth revisiting once content changes often enough for the manual step to become a bottleneck — this gets more pressing once the app is store-distributed, since a content-only update would then also require a full native rebuild + store review to reach users (see `docs/Deployment.md`).
- **Bundle size / code-splitting.** Total `dist/` output is ~1.8 MB, with the main JS chunk (~1.3 MB) as a single bundle. Route- or tab-based code-splitting (e.g. lazy-loading the Map tab's MapLibre dependency) could meaningfully reduce initial load time.
- **Unify `UserLocation` types.** `src/store/usePlacesStore.ts` and `src/hooks/useGeolocation.ts` each define their own `UserLocation` interface. They're structurally identical today but not shared, so they can silently drift apart. Worth consolidating into one shared type once either file changes for another reason.
- **Dependency review.** TypeScript has a new major version available (project is currently pinned to `~6.0.2`); worth a deliberate, tested upgrade pass rather than an incidental one. No other dependency was found duplicated or clearly obsolete as of this writing.
- **Populate `Experience.guideIds`.** The field exists in `src/data/types.ts` and `src/data/experiences.json`, but is `[]` on all 7 experiences today — no experience is actually linked to the guide(s) who run it. Populating it would let a future per-tour detail view show the relevant guide's bio (see the Experiences tab restructure, redesign v1 Empty and Error States addendum) instead of only a screen-wide "Meet the Guides" list.

## Low priority

- **`Collection` entity.** A `Collection` type is defined in `src/data/types.ts` with a corresponding (currently unused) `collectionsService.ts` stub removed in the v1.0.0 cleanup — no JSON data, no UI. If a themed "Collections" browsing mode (grouping places beyond category/tier) is ever wanted, this is the natural starting shape; if not, the type itself is a candidate for removal.
- **Settings screen.** Not present in any planning document or the codebase today, and explicitly confirmed as out of scope during this maintenance pass. Listed here only so a future decision to add one is deliberate, not assumed.
- **`maptiler`/`mapbox` map providers.** Defined as inactive options in `src/config/mapProvider.config.ts`, pending a post-launch review of whether OSM raster tiles remain sufficient (styling, rate limits, attribution requirements).
